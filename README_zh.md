# X "为你推荐" (For You) Feed 算法

本仓库包含了驱动 X 平台上 "为你推荐" (For You) Feed 的核心推荐系统。它结合了网内内容（来自你关注的账号）和网外内容（通过基于机器学习的检索发现），并使用基于 Grok 的 Transformer 模型对所有内容进行排序。

> **注意：** Transformer 的实现是从 xAI 的 [Grok-1 开源版本](https://github.com/xai-org/grok-1) 移植而来的，并针对推荐系统场景进行了调整。

## 概览

"为你推荐" Feed 算法从两个来源检索、排序和过滤帖子：

1. **网内 (In-Network, Thunder)**：来自你关注的账号的帖子。
2. **网外 (Out-of-Network, Phoenix Retrieval)**：从全球语料库中发现的帖子。

这两个来源的内容被合并，并使用 **Phoenix**（一个基于 Grok 的 Transformer 模型）进行统一排序，该模型预测每条帖子的参与概率。最终得分是这些预测参与度的加权组合。

我们消除了系统中每一个人工设计的特征（Hand-engineered feature）和大部分启发式规则。基于 Grok 的 Transformer 通过理解你的参与历史（你点赞、回复、分享过的内容等）来承担所有重任，并以此确定哪些内容与你相关。

## 组件

### Home Mixer

**位置：** [`home-mixer/`](home-mixer/)

组装 "为你推荐" Feed 的编排层。它利用 `CandidatePipeline` 框架，包含以下阶段：

| 阶段 | 描述 |
|-------|-------------|
| 查询填充器 (Query Hydrators) | 获取用户上下文（参与历史、关注列表） |
| 来源 (Sources) | 从 Thunder 和 Phoenix 检索候选 |
| 填充器 (Hydrators) | 为候选添加附加数据 |
| 过滤器 (Filters) | 移除不符合条件的候选 |
| 打分器 (Scorers) | 预测参与度并计算最终得分 |
| 选择器 (Selector) | 按得分排序并选择前 K 个 |
| 选择后过滤器 (Post-Selection Filters) | 最终的可见性和去重检查 |
| 副作用 (Side Effects) | 缓存请求信息以供未来使用 |

服务器暴露了一个 gRPC 端点 (`ScoredPostsService`)，用于返回指定用户的已排序帖子。

---

### Thunder

**位置：** [`thunder/`](thunder/)

一个内存中的帖子存储和实时采集流水线，用于跟踪所有用户的最新帖子。它：

- 从 Kafka 消费帖子的创建/删除事件
- 为每个用户维护原始帖子、回复/转发和视频帖子的存储
- 为请求用户提供来自其关注账号的“网内”候选帖子
- 自动清理超过保留期的旧帖子

Thunder 能够实现亚毫秒级的网内内容查找，而无需访问外部数据库。

---

### Phoenix

**位置：** [`phoenix/`](phoenix/)

包含两个主要功能的机器学习组件：

#### 1. 检索 (双塔模型)
查找相关的网外帖子：
- **用户塔 (User Tower)**：将用户特征和参与历史编码为嵌入向量
- **候选塔 (Candidate Tower)**：将所有帖子编码为嵌入向量
- **相似度搜索**：通过点积相似度检索前 K 个帖子

#### 2. 排序 (具有候选隔离功能的 Transformer)
预测每个候选的参与概率：
- 以用户上下文（参与历史）和候选帖子作为输入
- 使用特殊的注意力掩码，使候选贴之间无法相互关注
- 输出各种动作类型（点赞、回复、转发、点击等）的概率

详见 [`phoenix/README.md`](phoenix/README.md) 获取详细的架构文档。

---

### Candidate Pipeline

**位置：** [`candidate-pipeline/`](candidate-pipeline/)

用于构建推荐流水线的可重用框架。定义了以下 Trait：

| Trait | 用途 |
|-------|---------|
| `Source` | 从数据源获取候选 |
| `Hydrator` | 为候选丰富额外的特征 |
| `Filter` | 移除不应显示的候选 |
| `Scorer` | 计算排序得分 |
| `Selector` | 排序并选择顶级候选 |
| `SideEffect` | 运行异步副作用（缓存、日志） |

该框架在可能的情况下并行运行来源（Source）和填充器（Hydrator），并具有可配置的错误处理和日志记录。

## 工作原理

### 流水线阶段

1. **查询填充 (Query Hydration)**：获取用户最近的参与历史和元数据（如：关注列表）。

2. **候选来源获取 (Candidate Sourcing)**：从以下位置检索候选：
   - **Thunder**：关注账号的最新帖子（网内）。
   - **Phoenix 检索**：从全球语料库中通过机器学习发现的帖子（网外）。

3. **候选填充 (Candidate Hydration)**：为候选丰富以下内容：
   - 核心帖子数据（文本、媒体等）。
   - 作者信息（用户名、认证状态）。
   - 视频时长（针对视频帖子）。
   - 订阅状态。

4. **打分前过滤 (Pre-Scoring Filters)**：移除以下帖子：
   - 重复项。
   - 太旧的内容。
   - 观看者自己的帖子。
   - 来自被屏蔽/静音账号的内容。
   - 包含屏蔽词的内容。
   - 之前看过或最近刚提供过的内容。
   - 不符合条件的订阅内容。

5. **打分 (Scoring)**：按顺序应用多个打分器：
   - **Phoenix 打分器**：从 Phoenix Transformer 模型获取机器学习预测。
   - **加权打分器**：将预测结果合并为最终的相关性得分。
   - **作者多样性打分器**：为保证多样性，减弱重复作者的得分。
   - **网外 (OON) 打分器**：针对网外内容调整得分。

6. **选择 (Selection)**：按得分排序并选择前 K 个候选。

7. **选择后处理 (Post-Selection Processing)**：对待提供的候选帖子进行最终验证。

---

### 打分与排序

基于 Grok 的 Phoenix Transformer 模型预测多种参与类型的概率：

```
预测结果：
├── P(喜欢/收藏)
├── P(回复)
├── P(转发)
├── P(引用)
├── P(点击)
├── P(个人资料点击)
├── P(视频播放)
├── P(图片展开)
├── P(分享)
├── P(停留时长)
├── P(关注作者)
├── P(不感兴趣)
├── P(屏蔽作者)
├── P(静音作者)
└── P(举报)
```

**加权打分器**将这些预测合并为最终得分：

```
最终得分 = Σ (权重_i × P(动作_i))
```

正面动作（点赞、转发、分享）具有正权重。负面动作（屏蔽、静音、举报）具有负权重，从而降低用户可能不喜欢的帖子的排名。

## 过滤

过滤器在两个阶段运行：

**打分前过滤器：**
| 过滤器 | 用途 |
|--------|---------|
| `DropDuplicatesFilter` | 移除重复的帖子 ID |
| `CoreDataHydrationFilter` | 移除未能成功填充核心元数据的帖子 |
| `AgeFilter` | 移除超过阈值的旧帖子 |
| `SelfpostFilter` | 移除用户自己的帖子 |
| `RepostDeduplicationFilter` | 对同一内容的转发进行去重 |
| `IneligibleSubscriptionFilter` | 移除用户无法访问的付费订阅内容 |
| `PreviouslySeenPostsFilter` | 移除用户已经看过的帖子 |
| `PreviouslyServedPostsFilter` | 移除在本会话中已经提供过的帖子 |
| `MutedKeywordFilter` | 移除包含用户屏蔽词的帖子 |
| `AuthorSocialgraphFilter` | 移除来自被屏蔽/静音作者的帖子 |

**选择后过滤器：**
| 过滤器 | 用途 |
|--------|---------|
| `VFFilter` | 移除已删除/垃圾信息/暴力/血腥等帖子 |
| `DedupConversationFilter` | 对同一对话线程的多个分支进行去重 |

## 关键设计决策

### 1. 无人工设计特征 (No Hand-Engineered Features)
系统完全依赖基于 Grok 的 Transformer 从用户参与序列中学习相关性。不需要人工为内容相关性设计特征。这显著降低了数据流水线和提供服务的基础设施的复杂性。

### 2. 排序阶段的候选隔离 (Candidate Isolation)
在 Transformer 推理期间，候选贴之间无法相互关注——只能关注用户上下文。这确保了帖子的得分不取决于批次中存在的其他帖子，使得分保持一致且可缓存。

### 3. 基于哈希的嵌入 (Hash-Based Embeddings)
检索和排序均使用多个哈希函数进行嵌入查找。

### 4. 多动作预测 (Multi-Action Prediction)
模型不是预测单一的“相关性”得分，而是预测许多种行为的概率。

### 5. 可组合的管道架构 (Composable Pipeline Architecture)
`candidate-pipeline` crate 提供了一个灵活的框架来构建推荐流水线，具有：
- 流水线执行和监控与业务逻辑的分离
- 独立阶段的并行执行和优雅的错误处理
- 能够轻松添加新的来源、填充、过滤器和打分器
