# 精排策略模式重构记录

> 本文档沉淀一次对 `services/ranker_service.py` 的架构改造：把**硬编码单一打分链路**改为**策略模式**，让方案 A/B/C/D（规则 / Phoenix / DeepCTR / LLM）都成为对等可插拔的策略，仅通过环境变量切换。
>
> 目标读者：后续维护精排服务、接入新策略或排查线上降级问题的工程师。
>
> 版本：1.0（2026-04-23）

---

## 1. 背景与动机

### 1.1 重构前的状态

`services/ranker_service.py` 的主干逻辑把"模型初始化 + 特征构建 + 推理 + 结果组装"绑死成一条路径：

- `_init_model` 直接构造 `RecsysInferenceRunner`（Phoenix Transformer）；
- `/v1/rank` 端点内嵌 `_feature_store.build_recsys_batch → _ranker.rank(...) → 19 个 p_* 字段解包`；
- `model_version` 只反映 Phoenix 权重；
- 模型异常 = 服务 500，没有降级路径。

### 1.2 问题

| 问题 | 后果 |
|------|------|
| 想加一条"规则兜底"分支要改核心文件 | A/B/C/D 四种方案互相干扰 |
| 没有预训练 checkpoint 时，服务返回的其实是**随机权重分数** | 上游业务感知不到，可能把随机分当真实打分用 |
| 模型 OOM / 推理异常直接 500 | 缺少自然降级 |
| DeepCTR、LLM 这类**需要不同推理后端**的方案无处挂载 | 每次接入都要改 `ranker_service.py` |

### 1.3 目标

- **服务层与策略层解耦**：`ranker_service.py` 只依赖 `RankingStrategy` 抽象，具体打分实现在子模块；
- **配置切换**：环境变量 `RANKER_STRATEGY` 决定用哪一种策略，不改代码；
- **降级链路内置**：支持"主策略 + 兜底策略"的组合，主策略异常时自动走备用；
- **扩展成本可控**：新增策略只需要实现一个类，不碰服务核心。

## 2. 架构设计

### 2.1 模块划分

```
services/
├── ranker_service.py              # 服务层：FastAPI 端点，只持有 RankingStrategy
├── ranker_strategies/
│   ├── __init__.py                # 对外暴露 create_strategy / RankingStrategy
│   ├── base.py                    # RankingStrategy ABC + StrategyResult + StrategyError
│   ├── factory.py                 # create_strategy 工厂（别名解析、init-time 降级）
│   ├── phoenix_strategy.py        # 方案 B：Phoenix Transformer
│   ├── rule_strategy.py           # 方案 A：规则兜底 + _RuleScorer
│   ├── deepctr_strategy.py        # 方案 C：DeepCTR (桩，未装依赖时抛 StrategyError)
│   ├── llm_strategy.py            # 方案 D：LLM-as-Ranker (桩)
│   └── fallback_strategy.py       # 组合策略：运行时降级包装
├── config.py                      # +strategy / fallback_strategy / rule_post_metadata_path
└── feature_store.py               # +build_recsys_batch 基类抽象方法
```

### 2.2 核心抽象

**`RankingStrategy`**（`base.py`）：

```python
class RankingStrategy(abc.ABC):
    name: str = "base"

    @abc.abstractmethod
    async def score(
        self,
        user_id: str,
        candidate_ids: List[str],
        history_len: int = 32,
    ) -> StrategyResult: ...

    async def warmup(self) -> None: ...   # 可选预热
    async def close(self) -> None: ...    # 可选关闭
```

**约束**：
1. 只暴露 `score` 一个方法，入参仅 `user_id + candidate_ids`；
2. 策略内部自行调用 `FeatureStore` 构造特征，服务层不感知；
3. 一次性开销（模型加载、JIT）在 `__init__` 完成；
4. 对外统一 `async`，便于未来接远程后端。

**`StrategyResult`**：

```python
@dataclass
class StrategyResult:
    scores: np.ndarray              # [num_candidates, num_actions]
    ranked_indices: np.ndarray      # [num_candidates]
    strategy_name: str              # 便于监控/日志
    model_version: Optional[str]
```

`scores` 统一为 `[C, num_actions]` 形状；单目标策略（规则 / DeepCTR / LLM）可在 `num_actions` 维上复制主分数，服务层无需判断策略类型。

**`StrategyError`**：任何策略内部的可预期失败（模型未加载、依赖缺失、远程超时）都应包装成它；`FallbackStrategy` 和 `factory` 只捕获这一种异常类型，其他异常继续向上抛。

### 2.3 降级模型：两层降级

| 时机 | 实现 | 行为 | `strategy_name` |
|------|------|------|---------------|
| **初始化阶段** 主策略 `__init__` 抛 `StrategyError` | `factory.create_strategy` | fallback **晋升为主策略** 返回（不包装 `FallbackStrategy`） | 裸的 fallback 名（如 `rule`） |
| **运行时** 主策略 `score` 抛 `StrategyError` | `FallbackStrategy.score` | 每次请求动态调用 fallback | `primary->fallback` 箭头形式 |

这种设计的意图：
- 初始化失败通常是**永久性**的（如未装依赖），没必要每次请求都试一次主策略；
- 运行时失败可能是**瞬态**的（如单次超时），保留主策略仍然有机会；
- 通过 `strategy_name` 箭头标注，监控端可以区分"哪些请求走的是降级"。

## 3. 如何切换策略

### 3.1 环境变量速查

| 变量 | 取值 | 作用 |
|------|------|------|
| `RANKER_STRATEGY` | `phoenix` (默认) / `rule` / `deepctr` / `llm` / 别名 `a/b/c/d` | 选择主策略 |
| `RANKER_FALLBACK_STRATEGY` | 同上，可空 | 兜底策略名；留空则无降级 |
| `RANKER_CHECKPOINT_PATH` | 路径 | Phoenix / DeepCTR 的权重文件 |
| `RANKER_RULE_POST_META` | 路径 | Rule 策略可选：post `publish_time` parquet，启用 freshness |

> 别名映射定义在 `services/ranker_strategies/factory.py::_ALIASES`。

### 3.2 常用启动组合

```bash
# 1) 默认 phoenix (无 ckpt 时随机权重，建议只用于联调)
uv run python -m services.ranker_service

# 2) 规则兜底 (零模型，最稳)
RANKER_STRATEGY=rule uv run python -m services.ranker_service

# 3) 主 phoenix + 规则兜底 (推荐生产组合)
RANKER_STRATEGY=phoenix \
RANKER_FALLBACK_STRATEGY=rule \
  uv run python -m services.ranker_service

# 4) 加载真实 ckpt + 规则兜底 + 启用 freshness
RANKER_STRATEGY=phoenix \
RANKER_FALLBACK_STRATEGY=rule \
RANKER_CHECKPOINT_PATH=checkpoints/v1/model_params_step5000.npz \
RANKER_RULE_POST_META=data/post_metadata.parquet \
  uv run python -m services.ranker_service

# 5) DeepCTR (需先自行实现 _predict 并装依赖)
RANKER_STRATEGY=deepctr \
RANKER_CHECKPOINT_PATH=checkpoints/din.pt \
  uv run python -m services.ranker_service
```

### 3.3 代码内手动组装

用于测试或自定义参数场景：

```python
from services.config import RankerServiceConfig
from services.feature_store import create_feature_store
from services.ranker_strategies import create_strategy

cfg = RankerServiceConfig.from_env()
fs = create_feature_store("mock", emb_size=cfg.model.emb_size)
strategy = create_strategy("phoenix", cfg, fs, fallback="rule")
# 得到 FallbackStrategy(primary=PhoenixStrategy, fallback=RuleStrategy)
```

### 3.4 如何新增一种策略

按 5 步：

1. 在 `services/ranker_strategies/` 新建文件（如 `mytower_strategy.py`）；
2. 继承 `RankingStrategy`，设置 `name = "mytower"`，实现 `__init__` 和 `async score`；
3. `__init__` 内做所有一次性加载，失败时 `raise StrategyError("...")`；
4. 在 `factory.py::_ALIASES` 注册名称与别名；
5. 在 `factory.py::_create_single` 添加构造分支（用惰性 import 避免启动加载重依赖）。

测试：参照 `tests/test_strategy_factory.py::TestRuntimeFallback::test_score_failure_triggers_fallback` 写一个端到端用例。

## 4. 验证效果

### 4.1 功能验证脚本

```bash
uv run python -c "
import asyncio
from services.config import RankerServiceConfig
from services.feature_store import create_feature_store
from services.ranker_strategies import create_strategy

async def main():
    cfg = RankerServiceConfig.from_env()
    fs = create_feature_store('mock', emb_size=cfg.model.emb_size)

    # 场景 1：rule 策略
    rule = create_strategy('rule', cfg, fs)
    r1 = await rule.score('u1', ['p1','p2','p3','p4'], history_len=32)
    print(f'strategy={r1.strategy_name} version={r1.model_version}')
    print(f'scores shape={r1.scores.shape} primary={r1.scores[:,0].tolist()}')

    # 场景 2：phoenix + rule fallback
    combo = create_strategy('phoenix', cfg, fs, fallback='rule')
    r2 = await combo.score('u1', ['p1','p2','p3','p4'], history_len=32)
    print(f'strategy={r2.strategy_name} version={r2.model_version}')

    # 场景 3：deepctr (init fail) + rule → rule 晋升为主
    combo2 = create_strategy('deepctr', cfg, fs, fallback='rule')
    r3 = await combo2.score('u1', ['p1','p2'], history_len=16)
    print(f'strategy={r3.strategy_name} version={r3.model_version}')

asyncio.run(main())
"
```

### 4.2 实测输出（2026-04-23）

```
=== RULE STRATEGY ===
strategy=rule version=rule-v1
scores shape=(4, 19)  ranked_indices=[0, 1, 2, 3]
primary action probs=[0.325, 0.125, 0.125, 0.125]

=== PHOENIX + RULE FALLBACK ===
Phoenix strategy: using random initialization (no checkpoint provided)
strategy=phoenix version=random
scores shape=(4, 19)  ranked_indices=[0, 1, 2, 3]

=== DEEPCTR (expect init fail) + RULE ===
primary strategy 'deepctr' init failed (...requires torch and deepctr-torch...);
using fallback 'rule' as primary
strategy=rule version=rule-v1
```

### 4.3 结果解读

**场景 1 (规则策略)**：
- p1 得 0.325 = freshness(0.5)×0.25 + 一个单分信号×0.20 = 0.125 + 0.20；
- p2/p3/p4 = 0.125 只拿到 freshness 中性分，没有命中 affinity/surface；
- 说明四个信号按权重正确合成。

**场景 2 (phoenix 主 + rule 兜底)**：
- Phoenix 随机初始化成功，推理无异常 → `FallbackStrategy` 未触发运行时降级；
- `strategy_name=phoenix` 保持不变；`version=random` 由策略显式标注；
- `ranked_indices=[0,1,2,3]` 是随机权重 + sigmoid 的典型现象（logits 接近 0 → 概率挤在 0.5），`argsort` 稳定排序保原序。

**场景 3 (DeepCTR 主 + rule)**：
- DeepCTR 因缺可选依赖在 `__init__` 抛 `StrategyError`；
- `factory` 直接把 rule 晋升为主（而不是包成 `FallbackStrategy`）；
- `strategy_name=rule`，无箭头。

## 5. 遇到的问题与决策

| 问题 | 决策 | 理由 |
|------|------|------|
| 策略的接口输入用 `(batch, embeddings)` 还是 `(user_id, candidate_ids)`？ | 选后者 | 解耦特征层；未来对接 Redis/远端 FeatureStore 时服务层不变 |
| `FeatureStore` 基类没声明 `build_recsys_batch`，只 `MockFeatureStore` 有 | 提升为抽象方法 | 原 `ranker_service.py` 已事实依赖，补齐基类消除松散类型 |
| DeepCTR/LLM 暂未实现，要不要先跳过？ | 提供桩 + `StrategyError` | 让工厂降级路径能被真实触发和测试，避免以后接入时再改工厂 |
| 初始化期失败是否也包一层 FallbackStrategy？ | 直接晋升 fallback 为主 | 永久性失败时每请求都试一次主策略没有收益；晋升后日志/监控也更干净 |
| 统一 `scores=[C, num_actions]` 会让单目标策略（如 rule）浪费内存 | 接受，但用 `np.tile` 共享底层 | 服务层组装响应的代码不需要分支判断，可维护性更高 |
| ty 对可选依赖 (`torch`, `deepctr_torch`) 报 `Cannot resolve imported module` | 保留不修 | 运行时 `try/except ImportError` 已处理；桩策略就是要在未装依赖时 fail |
| `pytest-asyncio` 没安装，但测试需要跑 async | 用 `asyncio.run(...)` 手动包 | 避免新增依赖；项目没有其他异步测试需要 |

## 6. 注意事项

### 6.1 上线与回滚

- **首次上线**：建议先 `RANKER_STRATEGY=rule` 小流量跑一段，排除上游调用链路问题，再切换到 `phoenix` 或 `phoenix + rule fallback`；
- **回滚**：不需要发布，直接改环境变量重启即可；
- **监控**：重点看 `RankResponse.strategy` 字段——如果线上大量出现 `phoenix->rule`，说明主策略抛了 `StrategyError`，应该排查模型推理失败原因。

### 6.2 性能

- `RuleStrategy` 是纯 numpy，耗时在毫秒级，可作为性能安全网；
- `PhoenixStrategy` 首次请求因 JAX JIT 编译较慢（秒级），后续请求毫秒级。上线前用 `warmup` 预热；
- `FallbackStrategy` 只在主策略抛错时走 fallback，正常请求**没有额外开销**；
- 注意策略构造只做一次（在 `lifespan` 里），不要在 `/v1/rank` 请求路径里重复 `create_strategy`。

### 6.3 不要混淆的两件事

- `strategy_name` **不等于** `model_version`：
  - `strategy_name=phoenix, version=random` 是**随机权重的 Phoenix**，不代表模型已训练；
  - `strategy_name=rule, version=rule-v1` 永远等价，因为规则策略没有可变权重。
- **初始化期降级**与**运行时降级**是两条不同路径，`strategy_name` 格式不同：
  - 初始化期：直接是 fallback 名，如 `rule`；
  - 运行时：带箭头，如 `phoenix->rule`。

### 6.4 不要把随机权重模型当真实模型用

`PhoenixStrategy` 在找不到 checkpoint 时会随机初始化并继续运行。这是为了方便联调，但：
- 所有候选的打分会挤在 0.5 附近（sigmoid(接近 0)），**排序等同于随机**；
- 监控指标会失真（CTR/AUC 没有意义）；
- 生产环境**必须**提供 `RANKER_CHECKPOINT_PATH`，或者让 `RANKER_STRATEGY=rule` 作主策略；
- 观察到日志 `Phoenix strategy: using random initialization` 就说明触发了这个情况。

### 6.5 策略内部必须抛 `StrategyError` 而不是通用异常

否则 `FallbackStrategy` 不会捕获，异常会穿透到 FastAPI 返回 500：

```python
# ✅ 正确
try:
    out = self._runner.rank(batch, embeddings)
except Exception as exc:
    raise StrategyError(f"phoenix inference failed: {exc}") from exc

# ❌ 错误：直接抛 RuntimeError，fallback 不会触发
out = self._runner.rank(batch, embeddings)
```
