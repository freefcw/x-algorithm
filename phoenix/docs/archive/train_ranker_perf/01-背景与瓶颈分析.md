# 01 — 背景与瓶颈分析

> 原脚本：`@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py`
> 分析范围：训练入口 `train()` 的全链路（数据加载 → 查表 → 前向/反向 → 优化 → checkpoint）

---

## 1. 起因

用户反馈：

> 当下 `scripts/train_ranker.py` 执行速度很慢，有什么办法可以优化这个脚本的执行速度吗？

第一时间读完全文件（379 行）后，发现这是一份"功能正确但性能裸奔"的脚本：能跑通，但每一个关键环节都有额外开销，且在真实数据上容易出各种奇怪现象。

## 3. 瓶颈逐点审计

### 3.1 【高】Parquet 加载每个文件只产 1 个 batch

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:220-240
    try:
        import pyarrow.parquet as pq
    except ImportError:
        raise ImportError("读取 Parquet 需要安装 pyarrow：uv add pyarrow")

    table = pq.read_table(parquet_path)
    df = table.to_pydict()
    n = min(batch_size, len(df["user_hashes"]))

    batch = RecsysBatch(
        user_hashes=np.array(df["user_hashes"][:n], dtype=np.int32),
        history_post_hashes=np.array(df["history_post_hashes"][:n], dtype=np.int32),
        ...
    )
    labels = np.array(df["labels"][:n], dtype=np.float32)
    return batch, labels
```

- 每次 `pq.read_table` **读整份文件**（实际项目里单文件可达 1–2 GB），然后 `to_pydict()` 把所有行转成 Python 嵌套 list。
- 但只从中切 `n = min(batch_size, ...)` = 几行出来用，其余全部丢弃。
- 嵌套 `list[list[int]] → np.array(dtype=int32)` 是 Python 逐元素路径，极慢。

**外层循环还把这个低效路径再放大一次**：

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:324-331

        # 数据来源：真实 Parquet 或模拟数据

        else:
            data_iter = (make_simulated_batch(args.batch_size) for _ in range(args.steps))

        for batch, labels in data_iter:
```

每次外层 while 都**重新打开全部 Parquet 文件**，每个文件依然只贡献 1 个 batch。训练步数越多，浪费越大。

---

### 3.2 【高】每步 `float(loss_val)` 阻塞同步

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:338-345
            params, opt_state, loss_val = train_step(params, opt_state, batch, embeddings, labels_jnp)
            loss_accum += float(loss_val)
            step += 1

            if step % args.log_every == 0:
                avg_loss = loss_accum / args.log_every
                logger.info(f"step {step:5d} / {args.steps}  loss={avg_loss:.4f}")
```

JAX 的 `@jax.jit` 是**异步分派**的 —— `train_step` 返回时 `loss_val` 还只是一个 "future"。

`float(loss_val)` 会触发 `block_until_ready`：**CPU 必须等 device 把当前 step 完全算完才能继续**，无法与下一步的 H2D 拷贝或 `train_step` 调度流水线重叠。

结果：JAX 的异步执行优势被彻底抵消，整条训练循环退化成"一帧一等待"的同步循环。

---

### 3.3 【中】嵌入表在 CPU 上查表，再 host→device 拷贝

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:96-114
def lookup_embeddings(
    batch: RecsysBatch,
    user_emb: np.ndarray,
    post_emb: np.ndarray,
    author_emb: np.ndarray,
) -> RecsysEmbeddings:
    """根据 batch 中的哈希值查表，返回 RecsysEmbeddings。"""
    u_idx  = np.asarray(batch.user_hashes,              dtype=np.intp)
    hp_idx = np.asarray(batch.history_post_hashes,      dtype=np.intp)
    cp_idx = np.asarray(batch.candidate_post_hashes,    dtype=np.intp)
    ha_idx = np.asarray(batch.history_author_hashes,    dtype=np.intp)
    ca_idx = np.asarray(batch.candidate_author_hashes,  dtype=np.intp)
    return RecsysEmbeddings(
        user_embeddings=user_emb[u_idx],
        history_post_embeddings=post_emb[hp_idx],
        candidate_post_embeddings=post_emb[cp_idx],
        history_author_embeddings=author_emb[ha_idx],
        candidate_author_embeddings=author_emb[ca_idx],
    )
```

三张 100 001 × 128 的嵌入表（约 49 MB/张）每步都：

1. 用 numpy fancy indexing 在 CPU 上切出若干行；
2. 进 `train_step` 时隐式做 `numpy → device array` 拷贝。

两个环节都不小。而且查表**没有被 JIT**，XLA 无法和前向/反向算子融合。


### 3.5 【低】`loss_fn` 每次被 trace/调用都重建 config

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:145-157

    model_config = make_model_config()
    model_config.initialize()
```

`@jax.jit` 只 tracing 一次，所以影响小。列在这里是提醒：**写 JIT 过的函数时要把可预构造的 Python 对象提到外面**。本次优化中没有改这一处（收益太小）。

### 3.6 【致命但后发】数据量本身 ≫ 内存

光看代码看不到这一点，是真实数据跑到一半时才暴露的。`data/training_samples/` 下 8 个 Parquet 合计约 **28.7 M 行**，紧凑 numpy 下每行 ≈ 3.8 KB，展开到内存需要 **≈ 109 GB**。

"一次性加载"的 in-memory 方案在小样本上 OK，在全量上必然 OOM，且 macOS 内核 OOM 时会**静默杀进程**（exit code 仍为 0），表现为日志断档、没有报错。

这部分专门在 [03-OOM与流式训练.md](./03-OOM与流式训练.md) 展开。

## 4. 瓶颈汇总与优先级

| 编号 | 瓶颈 | 代码位置 | 影响 | 优化难度 |
|---|---|---|---|---|
| A | Parquet 每文件仅 1 batch、Python 嵌套 list 转 numpy | `load_parquet_batch` + `iter_parquet_dir` | 极高 | 中 |
| B | per-step `float(loss_val)` 阻塞同步 | 训练循环 338 行附近 | 高 | 低 |
| C | CPU 嵌入表查表 + host↔device 拷贝 | `lookup_embeddings` | 中 | 中 |
| D | 模拟数据 Python for | `runners.create_example_batch` | 低 | 低 |
| E | 外层 while 每轮重开目录 | 训练循环 324 行附近 | 中 | 低 |
| F | `loss_fn` 内重建 config | `loss_fn` | 忽略 | - |
| G | 全量数据 OOM | 架构级 | 致命 | 中 |

---

## 5. 到此为止的结论

- 收益面上，**A 最大、B 次之、C/E 中等、D/F 很小**。
- 架构层面，**G 决定了能不能跑全量数据**，必须单独解方案。
