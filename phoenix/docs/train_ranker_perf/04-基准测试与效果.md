# 04 — 基准测试与效果

> 有了优化代码，就得有**可复现、可对比的量化基线**。这一篇说 `--benchmark` 开关是怎么实现的，当前实测数字，以及下一步往哪里拧。

---

## 1. benchmark 开关设计

### 1.1 为什么单独做一个开关

训练循环本身混杂了数据加载、logging、checkpoint 保存等"非 step 本身"的事情。想量化"单步纯计算"耗时必须把它们隔离开。

做法：在训练循环**之后**追加一段纯 step 测量段，不写 checkpoint、不打 loss，只跑 warmup + 计时两个阶段。

### 1.2 实现

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:621-651
    # 8. 可选 benchmark：训练循环之后追加一段稳态 step 计时（不会写 checkpoint）
    if args.benchmark:
        import time
        warmup = max(0, args.warmup_steps)
        bench = max(1, args.benchmark_steps)
        logger.info(f"[bench] warmup={warmup} 步，计时={bench} 步，batch={args.batch_size}")
        for _ in range(warmup):
            batch, labels = next(data_iter)
            batch_dev = jax.tree_util.tree_map(jnp.asarray, batch)
            labels_dev = jnp.asarray(labels)
            params, opt_state, loss_val = train_step(
                params, opt_state, batch_dev, labels_dev
            )
        # barrier：确保 warmup 都落盘后再开始计时
        jax.block_until_ready(loss_val)
        t0 = time.perf_counter()
        for _ in range(bench):
            batch, labels = next(data_iter)
            batch_dev = jax.tree_util.tree_map(jnp.asarray, batch)
            labels_dev = jnp.asarray(labels)
            params, opt_state, loss_val = train_step(
                params, opt_state, batch_dev, labels_dev
            )
        jax.block_until_ready(loss_val)
        dt = time.perf_counter() - t0
        step_ms = dt / bench * 1000
        samples_per_sec = bench * args.batch_size / dt
        logger.info(
            f"[bench] avg_step={step_ms:.2f} ms, samples/sec={samples_per_sec:.1f} "
            f"({bench} steps after {warmup} warmup)"
        )
```

关键点：
- **warmup** 用来消耗 JIT 编译、pyarrow 缓冲预热、磁盘 cache 预热这些"一次性成本"；
- 计时前后各做一次 `jax.block_until_ready(loss_val)` 作为 barrier，确保 `dt` 包含的是"完整完成的 step 数量"；
- 打印 `avg_step` 与 `samples/sec` 两个核心数字。

### 1.3 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--benchmark` | off | 开启 benchmark 段 |
| `--warmup-steps` | 10 | 热身步数，不计入结果 |
| `--benchmark-steps` | 50 | 计时步数 |

## 2. 实测数据

**硬件 / 环境**：macOS aarch64（Apple Silicon），JAX 默认 CPU backend（Metal/TPU 都没加载），batch_size = 64。

| 模式 | 数据源 | 命令关键参数 | avg_step | samples/sec |
|---|---|---|---|---|
| 模拟 | 内存向量化 | `--steps 0 --benchmark` | **24.15 ms** | 2650.3 |
| in-memory | 20 k 样本 | `--data-dir ... --max-samples 20000 --benchmark` | **24.35 ms** | 2628.7 |
| streaming | 全量 29 M 样本 | `--data-dir ... --streaming --shuffle-buffer 16384 --benchmark` | **25.72 ms** | 2488.4 |

### 2.1 观察

1. **三种模式的 step 时间都在 24–26 ms 范围内，相差不到 7%**。这说明数据侧已经完全不是瓶颈 —— 如果数据准备慢，streaming 模式的数字会明显劣化，但并没有。
2. **streaming 比 in-memory 慢约 6%**，差值主要来自 pyarrow IO 和 shuffle buffer 的拷贝。这个代价换来了"跑全量 29 M 样本不 OOM"，划算。
3. **`train_step` 自身已成为瓶颈**。要继续加速，得从模型本身想办法。

### 2.2 复现

```bash
# 模拟
uv run scripts/train_ranker.py --steps 0 --batch-size 64 \
  --benchmark --warmup-steps 10 --benchmark-steps 100 \
  --ckpt-dir /tmp/bench_sim

# in-memory
uv run scripts/train_ranker.py --data-dir data/training_samples \
  --max-samples 20000 --steps 0 --batch-size 64 \
  --benchmark --warmup-steps 10 --benchmark-steps 100 \
  --ckpt-dir /tmp/bench_mem

# streaming
uv run scripts/train_ranker.py --data-dir data/training_samples \
  --streaming --shuffle-buffer 16384 \
  --steps 0 --batch-size 64 \
  --benchmark --warmup-steps 10 --benchmark-steps 100 \
  --ckpt-dir /tmp/bench_stream
```

## 3. 改动前的估算（无精确回归数据）

本次优化**没有保留**改动前的代码分支，所以下面是代码路径级的**估算**，不是实测：

| 环节 | 改动前（每步开销） | 改动后 | 估算节省 |
|---|---|---|---|
| Parquet 数据准备 | 100 ms ~ 几 s（读整个文件 + `to_pydict` + 嵌套 list 转 numpy） | 几十 μs（内存切片） | ~1000× |
| `float(loss_val)` 同步 | 5–50 ms（每步 block_until_ready） | 只在 log_every 步一次 | pipeline 异步化后整体 +30%~+200% 吞吐 |
| 嵌入表 CPU 查表 + H2D 拷贝 | 几到十几 ms | 融合进 JIT 的 `jnp.take`，~0 | 每步省 5–15 ms |
| 模拟数据 Python for | 1–3 ms | 几十 μs | 每步省 ~1 ms |
| 外层 while 每轮重开目录 | 每 `steps` 次外层循环重走一遍 | 无 | 数据模式下量级不定 |

**综合预期**：
- **真实数据模式**：整体吞吐 **~10–100×**（主要贡献来自数据加载重构）；
- **模拟数据模式**：整体吞吐 **~2–5×**（主要来自去 per-step 同步 + device-side lookup + 向量化）。

准确定量对比可以通过 git revert 当前改动、打回 `iter_parquet_dir` 版本、再跑一次相同 benchmark 命令得到。本次没有做，因为用户验收已经通过"全量数据能跑 + step 时间进入 25 ms 量级"的实测指标。

## 4. 下一步：如果还想继续加速

稳态 24 ms/step 的 0 代价极限已经到了。**要继续往下压，必须动模型本身**：

### 4.1 扩大 batch_size 摊薄 step overhead

目前 batch=64 时 step=24 ms。如果单步模型前反向本身占 ~20 ms、per-step 分派/启停占 ~4 ms，把 batch_size 翻倍到 128，理论 samples/sec 会提升 ~70%（而不是 100%）。这是免费午餐，值得做：

```bash
uv run scripts/train_ranker.py --data-dir data/training_samples \
  --streaming --batch-size 128 --steps 0 --benchmark
```

> 注意：batch_size 太大可能打满 CPU L2 cache 或者显存（GPU 时），需要配合硬件实际调。

### 4.2 混合精度（bfloat16 forward + float32 optimizer state）

当前 `loss_fn` 里强行 `fprop_dtype = jnp.float32`（训练时）：

```@/Users/hejun/work/mp/x-algorithm/phoenix/scripts/train_ranker.py:153-158
    model_config = make_model_config()
    model_config.initialize()
    model_config.fprop_dtype = jnp.float32  # 训练时用 float32 保证梯度精度
    model = model_config.make()
```

在 **GPU/TPU** 上改成 `bfloat16`（forward）+ float32（optimizer state）通常能再拿到 1.5–3× 提速。在 **CPU** 上不一定，因为现代 CPU SIMD 对 fp32 最友好，bf16 反而可能更慢 —— 需要实测。

### 4.3 设备本身

- 当前 `jax.local_devices()` 只有 CPU。
- 在 Apple Silicon 上接入 `jax-metal` 后端可以尝试 Metal GPU；但 JAX + Metal 的生态尚不成熟，可能有算子不支持。
- 若有 NVIDIA GPU，`jax[cuda12]` 的收益是最大的，step 时间常能压到 1 ms 以内。

### 4.4 多设备并行

如果上 GPU 并且 `jax.local_devices()` ≥ 2，可以把 `train_step` 用 `jax.pmap` 改成数据并行。当前代码结构已经为此准备好了（查表、loss 都是纯函数），改动量小。
