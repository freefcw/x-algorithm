# Phoenix 精排模型替代方案指引

> 目标读者：需要在 **Phoenix 仓库没有预训练精排权重** 的前提下，快速搭出一个"能用"的精排服务的工程师。
>
> 文档约定：**方案 A / B / C** 是三条优先推荐的可落地路径；**方案 D** 作为前沿对比组，仅给出接入思路与开销评估。

---

## 0. 现状速览

### 0.1 仓库提供了什么

| 类别 | 位置 | 是否开箱可用 |
|------|------|------------|
| 精排模型结构 (Transformer + 候选隔离 mask) | `recsys_model.py`、`grok.py` | ✅ |
| 推理封装 | `runners.py` 中 `RecsysInferenceRunner` | ✅ |
| 训练脚本 | `scripts/train_ranker.py` | ✅ 仅随机初始化 |
| 数据预处理 | `data_preprocessor.py`、`data_preprocessor_mp.py` | ✅ |
| HTTP 推理服务 | `services/ranker_service.py` | ✅ 默认随机权重 |
| 预训练 checkpoint | — | ❌ **不提供** |
| 真实大规模数据 | — | ❌ **不提供** |

### 0.2 为什么没有预训练大模型

1. **开源惯例**：推荐模型权重强依赖私域用户行为数据，X 团队只开源 recipe 不开源 weights；
2. **默认配置是"玩具尺寸"**：`scripts/train_ranker.py:32-38` 里的 `EMB_SIZE=128, HISTORY_LEN=32, NUM_CANDIDATES=8, TABLE_SIZE=100_000`，远小于生产 Heavy Ranker；
3. **Fallback 路径已内置**：`services/ranker_service.py:_init_model` 在找不到 checkpoint 时会走 `allow_random_init=True`，日志会打印 `Using random initialization (no checkpoint provided)`。

> **随机权重模型推理出的"概率"没有任何业务意义**——它能跑通流水线，但排序结果等价于随机打分。这就是为什么需要替代方案。

## 1. 方案总览

| 方案 | 一句话描述 | 投入 | 效果上限 | 适用阶段 |
|------|------------|------|---------|--------|
| **A. 规则兜底** | 不跑模型，用行为启发式给候选打分 | ★☆☆☆☆ (1 天) | ★★☆☆☆ | Demo / MVP / 模型训练未就绪时 |
| **B. 自训练 Phoenix** | 用你自己的日志走现有训练脚本 | ★★★☆☆ (1–2 周含数据) | ★★★★☆ | 有真实行为日志的场景 |
| **C. 开源成熟模型** | 接 DeepCTR / RecBole，薄适配层包回 Phoenix 接口 | ★★☆☆☆ (3–5 天) | ★★★★☆ | 算法团队不自研结构 |
| D. LLM-as-Ranker | 用 Llama/Qwen 等 LLM 做重排或教师模型 | ★★★★☆ | ★★★☆☆ → ★★★★★ | 研究 / 小流量实验 |

**推荐组合**：生产环境采用 **"方案 B 主模型 + 方案 A 兜底"**，在模型冷启或异常时走规则分；算法迭代期再叠加 **方案 D** 的 LLM 蒸馏实验。

## 2. 方案 A：规则兜底（零训练，最快跑通）

### 2.1 设计思路

精排的本质是"对候选集打分后排序"。在没有训练好的模型时，我们用四类启发式信号合成一个 `[0, 1]` 区间的分数，塞回 `services/ranker_service.py` 的响应里，**上游业务感知不到差异**。

四类信号：

1. **作者亲和度**：候选作者在用户历史中出现过 → 加分；
2. **场景匹配度**：候选 `product_surface` 与近期历史高频 `product_surface` 匹配 → 加分；
3. **新鲜度**：候选发布时间越近分数越高（需 `post_metadata.parquet`）；
4. **多样性惩罚**：同一作者在候选中出现多次，第二次及之后衰减。

最终 `score = w1*affinity + w2*surface_match + w3*freshness - w4*diversity_penalty`。

### 2.2 最小落地实现

#### 步骤 1：新建规则打分器

创建文件 `services/rule_scorer.py`：

```python
# services/rule_scorer.py
"""规则兜底打分器：零模型训练情况下提供稳定可解释的排序信号。"""

from __future__ import annotations

import time
from dataclasses import dataclass
from typing import Dict, List, Optional

import numpy as np

from recsys_model import RecsysBatch


@dataclass
class RuleScorerConfig:
    w_affinity: float = 0.35       # 作者亲和度权重
    w_surface: float = 0.20        # 场景匹配度权重
    w_freshness: float = 0.25      # 新鲜度权重
    w_diversity: float = 0.20      # 多样性惩罚权重

    freshness_half_life_hours: float = 12.0  # 新鲜度半衰期
    surface_topk: int = 3                     # 统计历史 top-k 高频 surface


class RuleScorer:
    """仅依赖 RecsysBatch 本身 + 可选的 post 元数据，即可对候选打分。"""

    def __init__(
        self,
        config: Optional[RuleScorerConfig] = None,
        post_publish_time: Optional[Dict[str, int]] = None,  # post_id -> unix_ts
    ):
        self.config = config or RuleScorerConfig()
        self.post_publish_time = post_publish_time or {}

    # ---- 单一信号 ----

    def _affinity_score(self, batch: RecsysBatch) -> np.ndarray:
        """候选作者是否出现在历史作者哈希中，返回 [B, C]。"""
        hist_authors = np.asarray(batch.history_author_hashes)  # [B, S, H]
        cand_authors = np.asarray(batch.candidate_author_hashes)  # [B, C, H]
        B, C, H = cand_authors.shape
        scores = np.zeros((B, C), dtype=np.float32)
        for b in range(B):
            hist_set = set(map(int, hist_authors[b].reshape(-1)))
            hist_set.discard(0)  # padding
            for c in range(C):
                cand_set = set(map(int, cand_authors[b, c]))
                cand_set.discard(0)
                if cand_set & hist_set:
                    scores[b, c] = 1.0
        return scores

    def _surface_score(self, batch: RecsysBatch) -> np.ndarray:
        hist_sur = np.asarray(batch.history_product_surface)     # [B, S]
        cand_sur = np.asarray(batch.candidate_product_surface)   # [B, C]
        B, C = cand_sur.shape
        scores = np.zeros((B, C), dtype=np.float32)
        for b in range(B):
            vals, counts = np.unique(hist_sur[b], return_counts=True)
            order = np.argsort(-counts)
            top = set(vals[order[: self.config.surface_topk]].tolist())
            for c in range(C):
                if int(cand_sur[b, c]) in top:
                    scores[b, c] = 1.0
        return scores

    def _freshness_score(
        self, candidate_ids: List[str], now_ts: Optional[int] = None
    ) -> np.ndarray:
        if now_ts is None:
            now_ts = int(time.time())
        half_life = self.config.freshness_half_life_hours * 3600.0
        out = np.zeros((1, len(candidate_ids)), dtype=np.float32)
        for i, cid in enumerate(candidate_ids):
            pub_ts = self.post_publish_time.get(cid)
            if pub_ts is None:
                out[0, i] = 0.5  # 未知发布时间：中性
                continue
            age = max(now_ts - pub_ts, 0)
            out[0, i] = float(0.5 ** (age / half_life))
        return out

    def _diversity_penalty(self, batch: RecsysBatch) -> np.ndarray:
        cand_authors = np.asarray(batch.candidate_author_hashes)  # [B, C, H]
        B, C, _ = cand_authors.shape
        out = np.zeros((B, C), dtype=np.float32)
        for b in range(B):
            seen: Dict[int, int] = {}
            # 先用 primary hash 作代表（第 0 列），简化实现
            primary = cand_authors[b, :, 0].tolist()
            for c, a in enumerate(primary):
                if a == 0:
                    continue
                cnt = seen.get(a, 0)
                out[b, c] = min(cnt * 0.5, 1.0)  # 同作者重复，惩罚递增
                seen[a] = cnt + 1
        return out

    # ---- 合成打分 ----

    def score(
        self,
        batch: RecsysBatch,
        candidate_ids: List[str],
        now_ts: Optional[int] = None,
    ) -> np.ndarray:
        """返回 [B, C] 的综合得分，已落在 [0, 1] 近似区间。"""
        cfg = self.config
        affinity = self._affinity_score(batch)
        surface = self._surface_score(batch)
        freshness = self._freshness_score(candidate_ids, now_ts=now_ts)
        penalty = self._diversity_penalty(batch)

        score = (
            cfg.w_affinity * affinity
            + cfg.w_surface * surface
            + cfg.w_freshness * freshness
            - cfg.w_diversity * penalty
        )
        return np.clip(score, 0.0, 1.0).astype(np.float32)
```

#### 步骤 2：让 `ranker_service` 支持"降级到规则分"

在 `services/ranker_service.py` 里做 **非侵入式** 改造：

- 新增环境变量 `RANKER_USE_RULE_FALLBACK=true` 控制是否启用；
- 若启用，**忽略模型 `rank` 输出的概率**，直接用规则分覆盖 `scores[:, :, 0]`（因为 `ranked_indices` 是基于 `probs[:, :, 0]` 排序的，见 `runners.py:356-359`）。

参考 diff（简化示意，不直接写入）：

```python
# services/ranker_service.py（增量改动示意）
from services.rule_scorer import RuleScorer  # 新增 import

_rule_scorer: Optional[RuleScorer] = None   # 全局单例

# 在 lifespan 里初始化
if os.getenv("RANKER_USE_RULE_FALLBACK", "false").lower() == "true":
    _rule_scorer = RuleScorer()
    logger.info("规则兜底打分器已启用")

# 在 /v1/rank 的推理后追加
if _rule_scorer is not None:
    rule_scores = _rule_scorer.score(batch, request.candidate_ids)  # [1, C]
    # 直接覆盖所有 action 的 scores，让排序完全由规则分决定
    scores = np.tile(rule_scores[0, :, None], (1, len(ACTIONS)))
    ranked_indices = np.argsort(-rule_scores[0])
```

> 这一步**不需要重训模型**，不需要新增依赖，只改 `ranker_service.py` 约 20 行。

#### 步骤 3：验证

```bash

RANKER_USE_RULE_FALLBACK=true uv run python -m services.ranker_service

# 另开终端测试

```

**验证要点**：

1. 同一用户不同候选的分数应随候选作者/场景变化（不再是模型随机输出的恒定分布）；
2. 同作者重复候选，第 2 个起分数应衰减；
3. 日志中不再出现 `Using random initialization` 导致的警告信号。

### 2.3 方案 A 的边界

| 能力 | A 是否支持 |
|------|-----------|
| 个性化（基于历史） | ✅ 简单 |
| 多目标打分（分别预测 favorite / reply） | ❌ 单一综合分 |
| 冷启动用户 | ✅ 退化为新鲜度排序 |
| 在线学习 | ❌ |
| AUC / NDCG 提升空间 | ❌ 天花板低 |

**结论**：方案 A 是**"流水线兜底"而非"效果方案"**。它的价值在于：
- 上游链路可以在真正的精排模型训练完成前就先上线；
- 模型异常时（OOM、推理超时）可以快速降级；
- 为后续方案 B/C 提供**可比较的 baseline**（如果一个学出来的模型 AUC 打不过规则分，就说明训练流程有问题）。

## 3. 方案 B：用自己的数据训练 Phoenix 精排

### 3.1 为什么选 B

- **零改结构**：直接复用 `recsys_model.py`、`scripts/train_ranker.py`、`data_preprocessor.py`；
- **产物可直接被服务加载**：`services/ranker_service.py:_init_model` 里的 `create_model_registry(config.checkpoint_path, allow_random_init=True)` 已经处理了 checkpoint 热加载。

### 3.2 数据准备 → 训练 → 上线 的完整路径

以下流程基于仓库既有脚本，全部可复现。

#### 步骤 1：准备原始日志

`data_preprocessor.py` 对输入的要求（见 `data_preprocessor.py:BEHAVIOR_FIELDS` 和 `load_behavior_logs`）：

**行为日志 Parquet**（`data/behavior_logs/dt=YYYY-MM-DD/*.parquet`）必须包含字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `user_id` | str | 用户 ID |
| `post_id` | str | 物品 ID |
| `author_id` | str | 作者 ID |
| `event_time` | int64 | Unix 时间戳（秒） |
| `product_surface` | int | 场景枚举，0–15 |
| 19 个行为字段 | 见下 | 0/1 或连续值 |

19 个行为字段与 `runners.py:ACTIONS` 对齐：
`favorite, reply, repost, photo_expand, click, profile_click, vqv, share, share_via_dm, share_via_copy_link, dwell, quote, quoted_click, follow_author, not_interested, block_author, mute_author, report, dwell_time`。

**帖子元数据 Parquet**（`data/post_metadata.parquet`）：

| 字段 | 类型 | 必填 |
|------|------|------|
| `post_id` | str | ✅ |
| `author_id` | str | ✅ |
| `is_active` | int | ❌（缺省视为 1，参与负样本池） |

> 若原始数据是 CSV，用 `examples/feed_csv_importer.py` 先转换为 Parquet。

#### 步骤 2：生成训练样本

```bash

```

```
history_post_hashes:        list[list[int32]] 形状 [32, 2]
history_author_hashes:      list[list[int32]] 形状 [32, 2]
```

#### 步骤 3：训练（先小后大）

**先跑一轮"玩具训练"验证链路**：

```bash

uv run scripts/train_ranker.py \
  --data-dir data/training_samples \
  --ckpt-dir checkpoints/v1 \
  --steps 500 \
  --batch-size 4 \
  --lr 1e-4 \
  --log-every 20 \
  --save-every 100
```

Loss 应在前 50–100 步内从 ~13（19 个 sigmoid 交叉熵之和）下降到 6 以下；若不下降，先检查数据质量再动结构。

**然后放大模型和训练量**。默认配置在 `scripts/train_ranker.py:32-38`：

```python

HISTORY_LEN = 32
NUM_CANDIDATES = 8
TABLE_SIZE = 100_000
NUM_HASHES = 2
```

以及 `make_model_config` 中的 Transformer 配置（`scripts/train_ranker.py:119-140`）：

```python
TransformerConfig(
    emb_size=128, widening_factor=2,
```

**建议的放大档位**（单机 A10/A100 级显卡）：

| 档位 | `emb_size` | `num_layers` | `num_q_heads` | `HISTORY_LEN` | `TABLE_SIZE` | `batch_size` | 粗估参数量 |
|------|-----------|--------------|---------------|---------------|--------------|-------------|-----------|
| S (玩具) | 128 | 2 | 2 | 32 | 10 万 | 4 | 30 M |
| M (推荐起点) | 256 | 4 | 4 | 64 | 100 万 | 16 | 200 M |
| L (接近 X Heavy Ranker) | 512 | 8 | 8 | 128 | 1000 万 | 32 | 1.5 B+ |

修改 `scripts/train_ranker.py` 里的常量即可，无需动服务代码。

### 3.3 方案 B 的常见坑

| 症状 | 可能原因 | 解决 |
|------|---------|------|
| Loss 一直在 13 附近震荡 | `candidate_seq_len` 与数据里的候选数不一致 | 对齐 `PhoenixModelConfig.candidate_seq_len` 与 `data_preprocessor.CANDIDATE_SEQ_LEN` |
| favorite 的 AUC 接近 0.5 | 正负样本未按用户切分，存在泄漏 | 按 `user_id` 切 train/eval |
| 推理时 shape 报错 | 线上 candidate 数量 > 训练时的 `candidate_seq_len` | 训练时 `NUM_CANDIDATES` 取线上上限 |
| 新用户分数异常 | 历史全为 padding 时注意力全 mask | 在 feature_store 里给新用户填一个"最近热门帖"作为伪历史 |

## 4. 方案 C：接入开源成熟精排模型

### 4.1 为什么选 C

- **结构稳定**：DeepCTR-Torch 的 DIN / DCN / DeepFM、RecBole 的 SASRec 都是工业验证过的；
- **生态丰富**：自带 AUC/LogLoss 评估、特征工程、Early Stopping；
- **对 Phoenix 侵入小**：只需要一个薄适配层把打分结果塞回 `RankingOutput`。

**推荐选型**：

| 库 | 适合场景 | 装包难度 |
|---|---------|--------|
| **DeepCTR-Torch** | CTR 任务、特征丰富（ID + 连续值） | 低 |
| **RecBole** | 序列推荐（SASRec / BERT4Rec），行为历史为主 | 中 |
| **TorchRec (Meta)** | 超大规模 Embedding 分布式训练 | 高 |

本文以 **DeepCTR-Torch + DIN** 为例，因为它与 Phoenix 的"用户历史 + 候选"范式最匹配。

### 4.2 落地实现

#### 步骤 1：新增依赖

```bash
uv add torch deepctr-torch pandas scikit-learn
```

#### 步骤 2：数据转换

DeepCTR-Torch 要求**宽表**格式，而 Phoenix 的训练样本是嵌套 list。新增 `scripts/convert_to_deepctr.py`：

```python
# scripts/convert_to_deepctr.py
"""把 data/training_samples/*.parquet 转成 DeepCTR 宽表。"""

import argparse
from pathlib import Path
import numpy as np
import pandas as pd
import pyarrow.parquet as pq


def convert(input_dir: str, output_path: str, history_len: int = 32):
    rows = []
    for f in sorted(Path(input_dir).rglob("*.parquet")):
        tbl = pq.read_table(str(f)).to_pandas()
        for _, r in tbl.iterrows():
            user_hash = r["user_hashes"][0]
            hist_posts = [h[0] for h in r["history_post_hashes"]]
            # 展开 1 正 7 负为 8 行样本
            for c_idx, (cand_hashes, cand_auth, cand_sur, label) in enumerate(
                zip(r["candidate_post_hashes"], r["candidate_author_hashes"],
                    r["candidate_product_surface"], r["labels"])
            ):
                rows.append({
                    "user_id": user_hash,
                    "post_id": cand_hashes[0],
                    "author_id": cand_auth[0],
                    "surface": cand_sur,
                    "hist_post_seq": hist_posts,   # list
                    "hist_seq_len": sum(1 for p in hist_posts if p != 0),
                    "label_favorite": label[0],
                    "label_click": label[4],
                    "label_dwell": label[10],
                })
    df = pd.DataFrame(rows)
    df.to_parquet(output_path, index=False)
    print(f"converted: {len(df)} rows -> {output_path}")


if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--input-dir", required=True)
    p.add_argument("--output", required=True)
    args = p.parse_args()
    convert(args.input_dir, args.output)
```

#### 步骤 3：训练 DIN

新增 `scripts/train_deepctr_din.py`：

```python
# scripts/train_deepctr_din.py
"""DeepCTR-Torch DIN 精排训练脚本。"""

import pandas as pd
import torch
from deepctr_torch.inputs import SparseFeat, VarLenSparseFeat, get_feature_names
from deepctr_torch.models import DIN


def main(data_path: str, ckpt_path: str, target: str = "label_favorite"):
    df = pd.read_parquet(data_path)

    # 稀疏特征
    sparse_feats = [
        SparseFeat("user_id", vocabulary_size=100001, embedding_dim=32),
        SparseFeat("post_id", vocabulary_size=100001, embedding_dim=32),
        SparseFeat("author_id", vocabulary_size=100001, embedding_dim=16),
        SparseFeat("surface", vocabulary_size=16, embedding_dim=8),
    ]
    # 变长序列特征（历史）
    varlen_feats = [
        VarLenSparseFeat(
            SparseFeat("hist_post_seq", vocabulary_size=100001, embedding_dim=32,
                       embedding_name="post_id"),  # 共享 post_id 嵌入
            maxlen=32, length_name="hist_seq_len",
        ),
    ]
    feature_columns = sparse_feats + varlen_feats
    feature_names = get_feature_names(feature_columns)

    # 把 DataFrame 转成 dict of arrays
    model_input = {name: df[name].values for name in feature_names if name != "hist_post_seq"}
    # 历史序列需要 pad 到 maxlen=32
    hist_padded = [list(s)[:32] + [0] * (32 - len(s)) for s in df["hist_post_seq"]]
    model_input["hist_post_seq"] = torch.tensor(hist_padded)

    y = df[target].values

    model = DIN(
        dnn_feature_columns=feature_columns,
        history_feature_list=["post_id"],
        dnn_hidden_units=(256, 128, 64),
        task="binary",
        device="cuda" if torch.cuda.is_available() else "cpu",
    )
    model.compile("adam", "binary_crossentropy", metrics=["auc"])
    model.fit(model_input, y, batch_size=512, epochs=5, validation_split=0.1)

    torch.save(model.state_dict(), ckpt_path)
    print(f"saved: {ckpt_path}")


if __name__ == "__main__":
    import argparse
    p = argparse.ArgumentParser()
    p.add_argument("--data", required=True)
    p.add_argument("--ckpt", default="checkpoints/din.pt")
    p.add_argument("--target", default="label_favorite")
    main(p.parse_args().data, p.parse_args().ckpt, p.parse_args().target)
```

#### 步骤 4：接入 `ranker_service`

新增 `services/external_ranker.py` 适配层，把 DIN 输出包装成 Phoenix 的 `RankingOutput` 结构：

```python
# services/external_ranker.py
"""外部模型适配器：把 DeepCTR DIN 的输出塞回 Phoenix 的 rank 接口。"""

from typing import List
import numpy as np
import torch
from deepctr_torch.models import DIN

from recsys_model import RecsysBatch, RecsysEmbeddings
from runners import ACTIONS, RankingOutput


class DeepCTRAdapter:
    """实现与 RecsysInferenceRunner 兼容的 rank(batch, embeddings) 接口。"""

    def __init__(self, ckpt_path: str, feature_columns, history_feature_list):
        self.model = DIN(
            dnn_feature_columns=feature_columns,
            history_feature_list=history_feature_list,
            task="binary",
        )
        self.model.load_state_dict(torch.load(ckpt_path, map_location="cpu"))
        self.model.eval()

    def rank(self, batch: RecsysBatch, embeddings: RecsysEmbeddings) -> RankingOutput:
        # 把 RecsysBatch 转成 DIN 输入
        user_id = np.asarray(batch.user_hashes)[:, 0]            # [B]
        cand_posts = np.asarray(batch.candidate_post_hashes)[:, :, 0]   # [B, C]
        cand_auths = np.asarray(batch.candidate_author_hashes)[:, :, 0]
        cand_surs = np.asarray(batch.candidate_product_surface)
        hist_posts = np.asarray(batch.history_post_hashes)[:, :, 0]     # [B, S]
        hist_len = (hist_posts != 0).sum(axis=1)                         # [B]

        B, C = cand_posts.shape
        # DIN 一次打一个 (user, candidate) 对，所以需要 B*C 行展开
        with torch.no_grad():
            probs = np.zeros((B, C), dtype=np.float32)
            for b in range(B):
                feed = {
                    "user_id": np.full(C, user_id[b], dtype=np.int64),
                    "post_id": cand_posts[b].astype(np.int64),
                    "author_id": cand_auths[b].astype(np.int64),
                    "surface": cand_surs[b].astype(np.int64),
                    "hist_post_seq": np.tile(hist_posts[b][None, :], (C, 1)),
                    "hist_seq_len": np.full(C, hist_len[b], dtype=np.int64),
                }
                out = self.model.predict(feed, batch_size=C)
                probs[b] = out.flatten()

        # 把单目标 prob 复制成 19 个 action（兼容现有 overall_score 计算）
        scores = np.tile(probs[:, :, None], (1, 1, len(ACTIONS)))
        ranked_indices = np.argsort(-probs, axis=-1)

        # 构造 RankingOutput（其他 p_* 字段都复用同一 prob）
        fields = {f"p_{a}": scores[:, :, i] for i, a in enumerate(ACTIONS)}
        return RankingOutput(
            scores=scores,
            ranked_indices=ranked_indices,
            **fields,
        )
```

然后在 `services/ranker_service.py` 的 `lifespan` 中根据环境变量 `RANKER_BACKEND=deepctr_din` 切换：

### 4.3 方案 C 的收益与代价

| 项目 | 说明 |
|------|------|
| ✅ 自带 AUC/LogLoss 指标曲线 | DeepCTR 训练过程直接打印 |
| ✅ 有预置调参实验 | DIN 的 attention 激活、hidden units 都可调 |
| ✅ 冷启动表现更稳 | 特征工程层做得更细 |
| ❌ 丢失 Phoenix 的候选隔离 mask | DIN 是 pair-wise，不是 set-wise |
| ❌ 多目标（19 个 action）需改造 | 需要把 `task="binary"` 换成 multi-task head |

**何时选 C 而不是 B**：
- 团队没有 JAX 经验；
- 需要快速对比多个经典结构（DIN vs DCN vs DeepFM）；
- 希望有现成的 early stopping / learning rate schedule。

## 5. 方案 D：LLM-as-Ranker（对比组，仅概述）

> 该方案**不作为生产首选**，列出仅为完整性。若你已有 B 或 C 的 baseline，D 可用于**教师模型蒸馏**或**离线重排实验**。

### 5.1 三种接法

#### D.1 Zero-shot Prompt 重排

把 Top-K 候选的 post 文本 + 用户近期历史摘要塞进 prompt，让 LLM 输出排序列表。

```
# 典型 prompt
User recently liked: <post_1 text>, <post_2 text>, ...
Please rank the following candidates by relevance to this user:
1. <candidate_1 text>
2. <candidate_2 text>
...
Output the ranking as a JSON list.
```

- **代表工作**：RankGPT、LRL、RankVicuna；
- **代价**：LLM 推理延迟 100 ms – 数 s，QPS 难以支撑线上；
- **适用**：小流量实验、头部用户个性化重排。

#### D.2 LLM Embedding 做特征

用 LLM 的文本编码器（如 `bge-m3`、`e5-mistral-7b`）离线把每条 post 文本转成向量，**替换 Phoenix 嵌入表里 `post_emb_table`**。

- **改动点**：只需改 `scripts/train_ranker.py` 中 `init_embedding_tables`，从磁盘加载预计算的向量而非随机初始化；
- **收益**：语义相似帖子嵌入更接近，冷启动帖子有非零语义信号；
- **代价**：需要维护一个离线 embedding 管线（post → LLM → vector → Parquet）。

#### D.3 LLM 蒸馏到 Phoenix

- **做法**：LLM 对大量 (user, candidate) 对打软分，作为 soft label 训练 Phoenix；
- **收益**：线上只跑 Phoenix，效果接近 LLM；
- **代价**：蒸馏数据量大（百万对起步），LLM 推理成本高，工程链路复杂。

### 5.2 方案 D 的权衡矩阵

| 接法 | 线上延迟 | 训练成本 | 效果天花板 | 成熟度 |
|------|---------|---------|-----------|-------|
| D.1 Zero-shot 重排 | 极高 | 0 | 中（受 prompt 限制） | 研究阶段 |
| D.2 LLM Embedding | 低（预计算） | 中（GPU 离线跑） | 中高 | 工业可用 |
| D.3 蒸馏 | 低 | 高 | 高 | 前沿，少数团队在做 |

```
Week 1  ┬─ A 规则兜底上线（ranker_service 支持降级）
        │
Week 2  ┼─ 数据预处理跑通 → B 玩具训练验证链路

Week 4  ┼─ B 上生产 → A 作为兜底分支
        │
```

**关键检查点**：

## 8. FAQ

**Q1：能不能先只用方案 A 上线，不做方案 B？**
可以，但**方案 A 的排序质量不如训练过的模型**。长期 CTR 和停留时长会低于 B。

**Q2：没有 GPU 能跑方案 B 吗？**
能。M 档模型在 CPU 上大概 100 ms/step，2000 步约 3 小时；S 档更快。但训练数据量大时 CPU 会成为瓶颈。

**Q3：方案 B 训练好的模型在方案 A 兜底路径里还能用上吗？**
能。`services/ranker_service.py` 可以同时挂载模型和 `RuleScorer`，**当模型推理抛异常时降级到规则分**（需要在 `/v1/rank` 里加 try/except）。

**Q4：方案 C 的 DIN 能复用 Phoenix 的嵌入表吗？**
不能直接复用。Phoenix 用的是**多哈希嵌入**（`HashConfig.num_*_hashes=2`），DIN 是单哈希。如果想共享，需要把 DIN 的 `SparseFeat` 改成多哈希组合，工作量不小，不推荐。

**Q5：为什么不推荐一开始就上 LLM？**
- 线上延迟从 10 ms 级跳到秒级，改造 `ranker_service` 成本高；
- 缺少 LLM 对推荐任务 fine-tune 的公开数据集；
- 在 AUC 维度下，调好的 DIN/Phoenix 往往能打平未微调的 LLM 重排器。
