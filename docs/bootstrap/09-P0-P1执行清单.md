### A2. rec-bff 合同验收

已具备代码和测试，下一步只需要使用真实上游地址运行：

- 候选分页：`ListRecommendationCandidates`；
- 内容批量查询：`BatchGetRecommendationContents`；
- Viewer 关系：`GetViewerRelations`；
- 空结果、缺失内容和 RPC 错误不能混为一类；
- 内容字段必须包含 `recommendation_eligible` 和 `ineligible_reason`。

### A3. Home Mixer 真实规则链路准备

在不启用 Phoenix 的情况下，可以直接联调：

```text
rec-bff → RecommendationDataService
       → Home Mixer 内容补全
       → 关系过滤
       → 可见性/审核过滤
       → 去重和规则排序
       → Feed 响应
```

所需配置由部署环境提供：

```text
HOME_MIXER_MODE=degraded
MRPYQ_RECOMMENDATION_DATA_ADDR=<rec-bff gRPC 地址>
HOME_MIXER_REDIS_URL=<共享 Redis 地址>
```

这些地址未提供前，只能做 fake adapter 测试，不能宣称真实链路已经跑通。

### A4. Redis 集成验证

本机有 Redis 时执行：

cd /Users/hejun/work/mp/x-algorithm
cargo test -p home-mixer --test redis_feed_state --test redis_uas -- --ignored

需要覆盖 Redis 重启、连接超时、TTL、多实例共享和恢复后的状态一致性。

## B. 等待业务信息后才能执行

以下事项不应由本仓库猜测：

| 事项 | 需要确认的信息 |
|---|---|
| mrpyq 推荐候选 | 候选来源、排序字段、分页游标、候选生成逻辑、真实 gRPC 地址 |
| mrpyq 内容 | feed ID、作者 ID、正文、发布时间、删除和审核字段的真实来源 |
| Viewer 关系 | 关注、拉黑、被拉黑、静音、屏蔽词分别来自哪个服务/表 |
| ID 契约 | viewer、account、member、feed、author 的格式和映射关系 |
| 认证 | Home Mixer/rec-bff 调 mrpyq 的 mTLS、JWT、服务发现或白名单方案 |
| 审核策略 | 审核结果缺失或超时时是 fail-closed 还是允许降级 |
| 曝光口径 | 返回即曝光，还是客户端实际渲染才算曝光 |
| 行为事件 | click、dwell、favorite、reply、report 等事件的字段和归因窗口 |
| 数据保留 | 曝光、行为、用户 ID 的脱敏和保留期限 |
| 首版目标 | 目标 QPS、p95/p99、首屏条数、空 Feed 率和重复率 |

## C. P1：当前可以先做的代码/数据准备

即使真实地址尚未提供，也可以先完成：

1. 固定曝光事件 schema，至少包含：

   ```text
   request_id
   viewer_id
   feed_id
   candidate_source
   served_position
   model_version
   event_time
   ```

2. 为 Home Mixer 的 served-candidates sink 选定第一版落点：Kafka 或 JSONL；
3. 在 rec-bff/Home Mixer 联调测试中固定 request ID 的透传方式；
4. 用脱敏 fixture 验证曝光事件和返回 Feed 的候选、顺序、来源一致；
5. 对历史业务数据做字段盘点，确认能否构造 Phoenix 的用户历史行为序列；
6. 统计曝光、点赞、回复、举报和停留事件的数量与时间分布。
