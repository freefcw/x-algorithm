# 从演示到真实系统

> **这篇解决什么问题**：诚实盘点演示模式"假"在哪，以及要把这套系统接到真实平台上，还需要做哪些事。
> **读完你能做到什么**：对工作量有准确预期，知道每个缺口对应改哪里、参考哪篇文档。
> **前置条件**：跑通了[第四步](./05-第四步-跑通完整推荐链路.md)。

## 演示模式"假"在哪

| 环节 | 演示模式的做法 | 真实系统需要 | 改哪里 |
| --- | --- | --- | --- |
| 帖子数据 | thunder 启动时生成 200 条模拟帖子（`--demo-seed-posts`） | 非 demo 不经过 Thunder / Kafka：帖子由 mrpyq 关注收件箱与 FALLBACK 池提供、内容由 mrpyq `BatchGetRecommendationContents` 补全。Thunder 是整数 proto、无法承载真实 ObjectId，只保留为可选部件（业务把发帖/删帖事件写进 Kafka topic `in-network-events` 后可独立运行，见 `proto/definitions/in_network.proto`） | 以 mrpyq 为准；Thunder / Kafka 仅在需要独立实时网内缓存时再评估（`thunder/`，需先改 string ID proto） |
| 网内召回 | `HOME_MIXER_MODE=demo` 时 `ThunderSource` 打整数 Thunder（仅零填充演示 ID） | 非 demo 必须设置 `MRPYQ_RECOMMENDATION_DATA_ADDR`；`MrpyqInNetworkPostsClient` 用 24-hex ObjectId 拉 NETWORK inbox / FALLBACK 池。未设置则启动失败。当前把皮 `member_id` 放进 proto 的 `account_id` 字段，mrpyq 侧仍按账号键读收件箱，皮维度对齐待落地 | `home-mixer/clients/mrpyq_adapters.rs`；mrpyq 侧见 `docs/implementation/mrpyq-member-dimension-requirements.md` §2。不要把真实 ObjectId 送进 Thunder 的 `uint64 user_id` |
| viewer 关系（拉黑 / 静音 / 屏蔽词） | `DemoStratoClient` 固定返回关注列表 101~105 | 非 demo 已装配 `MrpyqStratoClient`，调 mrpyq `ViewerRelationService`（`proto/definitions/viewer_relation.proto`）取拉黑 / 被拉黑 / 静音 / 屏蔽词；mrpyq 侧尚未实现该 RPC，当前调用失败、关系为空、过滤不生效。关注列表没有 mrpyq 契约，保持为空 | mrpyq 实现 RPC 并与推荐侧同批上线（见 `docs/implementation/mrpyq-member-dimension-requirements.md` §4–§6）；`home-mixer/clients/mrpyq_adapters.rs` |
| 用户行为序列 | `DemoUserActionSequenceFetcher` 合成 32 条浏览记录 | 从你平台的行为日志系统读取（这是个性化的核心输入）。非 demo 已装配 `RedisUserActionSequenceStore`：独立 job `uas-worker` 消费行为事件（Kafka JSON，或开发时 stdin）写入 Redis ZSET，Home Mixer 读取最近 7 天。没有投影数据的用户 `PhoenixScorer` 整批走 `RuleFallbackScorer` | 把平台埋点按 `docs/home-mixer/07-config-and-params.md` 的事件 JSON 合同写入 Kafka topic，用 `cargo run -p home-mixer --features kafka --bin uas-worker` 消费；`action_type` 对应 `proto/definitions/phoenix_recsys.proto` 的 `ActionName` 编号 |
| 帖子内容 | `DemoTESClient` 为每条帖子编一句占位文本 | 非 demo 已由 `MrpyqTESClient` 通过 mrpyq `BatchGetRecommendationContents` 补作者（`creator_member_id`）、正文、`created_at_ms`、互动数与一级 `recommendation_eligible` | mrpyq 保证 `creator_member_id` 非空（为空的帖子会被 `CoreDataHydrationFilter` 丢弃）；`home-mixer/clients/mrpyq_adapters.rs` |
| 作者资料 | `DemoGizmoduckClient` 合成昵称 / 粉丝数 | 非 demo 是 `DisabledGizmoduckClient`，作者昵称 / 粉丝数为空；QueryBuilder 不依赖 Gizmoduck | 用真实 adapter 替换 `home-mixer/clients/gizmoduck_client.rs` 的 `DisabledGizmoduckClient`，只补齐作者资料；网络范围仍只由请求字段控制 |
| 内容审核 | Demo VF 显式 Allow | 非 demo 装配 `MrpyqFirstStageEligibilityClient`，只承载帖子维度的一级 `recommendation_eligible`（`FirstStageEligibleFilter` 已在前面消费同一标志）；viewer 级可见性没有数据源。未验证候选按 `HOME_MIXER_VF_FAILURE_POLICY` 处理，默认 `fail_closed` 丢弃 | 接 viewer 级准入（依赖上面的 viewer 关系 RPC），并确认漏返回 / 超时策略；`home-mixer/clients/mrpyq_adapters.rs`、`home-mixer/feature_policy.rs` |
| 已下发去重 | Demo 默认 `InMemoryFeedStateStore` 写进程内存 | 非 demo 必须配置 `HOME_MIXER_REDIS_URL`，`RedisFeedStateStore` 让多副本共享同一份有界下发历史；写失败返回 `Unavailable` | 复用现有 Redis，按 `docs/home-mixer/07-config-and-params.md` 配置 key 前缀、TTL 与超时 |
| 曝光归因 | 无 | 持久、幂等、带位置与事件类型的 served / feedback 事件流，作为训练归因的原始数据源；去重历史不是曝光日志 | 在响应成功后向 Kafka / 日志通道发曝光事件，离线落表；feedback RPC 尚不存在 |
| 模型权重 | 随机初始化（或你训练的 checkpoint） | 用真实行为数据持续训练、定期发版 | [第三步](./04-第三步-训练自己的模型.md) + [训练指引](../../phoenix/docs/训练指引.md) |
| 网外候选池 | Phoenix 网关默认合成 2000 条并现场编码；`run_demo.sh` 传 `--corpus-size 1000` | 离线批量编码全量帖子，建向量索引（FAISS/Milvus），定期刷新 | `phoenix/services/grpc_gateway.py` 的 `RetrievalEngine` |
| 已看过帖子 | 请求里不带 | 客户端维护曝光记录（`seen_ids` / 布隆过滤器字段协议已就绪） | 客户端 + `proto/definitions/home_mixer.proto` |

一个设计上的关键点：**这些演示环节全部是客户端接口（trait）的独立 `Demo*` 实现**。`HomeMixerConfig` 解析 `HOME_MIXER_MODE=demo`，`HomeMixerServer::build` 将 mode、features 和 `UasConfig` 显式传给 `PhoenixCandidatePipeline::assemble_with_uas()`，demo/degraded 依赖的选择不再经由环境变量。非 demo 下 `clients/mrpyq_adapters.rs::pipeline_adapters_from_env` 用 `MRPYQ_RECOMMENDATION_DATA_ADDR` 一次构造 TES / 网内 / 兜底 / 一级 VF / Strato 五个 mrpyq 适配器并注入；下发历史由 `HomeMixerConfig.feed_state` 显式选择：demo 默认进程内存，非 demo 必须提供 `HOME_MIXER_REDIS_URL`，否则拒绝启动；行为序列由 `HomeMixerConfig.uas` 选择：demo 默认合成序列，非 demo 读取 `UAS_REDIS_URL`（缺省复用 `HOME_MIXER_REDIS_URL`）上由 `uas-worker` 投影的数据；仍未接后端的端口（Gizmoduck）保持 `Disabled*` 实现，`production_ready` 在这些合同缺失时拒绝启动。可选依赖（VM Ranker、Phoenix MoE 等 `HOME_MIXER_ENABLE_*` 特性开关）仍从环境变量读取并在装配点注入。替换时实现对应 trait、在具名 `PhoenixDependencies` 装配处注入，并补齐合同验收，不需要改流水线或演示代码。

## 建议的推进顺序

1. **先通数据，再通模型**：先把 mrpyq 皮维度召回与 `creator_member_id` 必填落地，再接入 Gizmoduck 作者资料。此时用 `RuleFallbackScorer` 的规则排序就能得到“新鲜度 + 网内 + 互动”驱动的全网 Feed 骨架。
2. **积累行为日志，训练第一版模型**：先在响应成功后补一条曝光事件流（Redis 里的去重历史有界且带 TTL，不能当训练日志），再按[训练数据规格](../training/training_data_spec.md)落日志表，用[训练指引](../../phoenix/docs/训练指引.md)建立"日志 → 样本 → checkpoint"的例行任务；接上 UAS 适配器后 `PhoenixScorer` 才会真正调用模型。
3. **上线真实召回**：离线编码全量帖子建向量索引，替换演示候选池；索引切版和数据运维的设计建议见[数据运维手册](../operations/data_operations_runbook.md)。
4. **补齐工程保障**：调用方身份校验、灰度发布、降级策略（Phoenix 挂了或没有行为序列时自动退化为 `RuleFallbackScorer` 规则排序——这个行为现在就有）。健康检查（`/healthz`、`/readyz`）、RPC 级 Prometheus 指标、SIGTERM 优雅关停和请求总预算已在 home-mixer 落地，见 [07 配置](../home-mixer/07-config-and-params.md)；流水线阶段级指标仍缺。

## 已知的工程缺口

坦白列出目前代码里需要注意的点：

- thunder 已定义 Prometheus 指标但 metrics HTTP 路由尚未暴露；home-mixer 的 9090 端口已提供 `/healthz`、`/readyz`、`/metrics`，但指标只到 RPC 入口一层，source / filter / scorer 阶段仍只有日志。
- home-mixer 的请求总预算默认 10 s（`HOME_MIXER_REQUEST_TIMEOUT_MS`），只是兜底；真实客户端应自带更短的 `grpc-timeout`，服务端会取两者中更短者。
- thunder 不是等 Kafka 追平才打印 `Server ready`：每个消费线程处理完第一个满批次（默认 1000 条）就发 init；端口已监听，查询只返回已摄入的部分数据。小流量攒不满一个 batch 时 ready 可能一直不出现，把 `--kafka-batch-size` 调小。
- gRPC 网关是单进程 JAX 推理，生产需要按 QPS 做批处理和多副本（HTTP 版的生产化清单见 `phoenix/services/README.md`）。
- 各模块更细的风险清单在模块文档里：[home-mixer](../home-mixer/06-current-behavior-risks-roadmap.md)、[thunder](../thunder/06-risks-and-roadmap.md)、[candidate-pipeline](../candidate-pipeline/06-risks-tests-and-roadmap.md)。
