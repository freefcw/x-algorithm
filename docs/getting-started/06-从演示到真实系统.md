# 从演示到真实系统

> **这篇解决什么问题**：诚实盘点演示模式"假"在哪，以及要把这套系统接到真实平台上，还需要做哪些事。
> **读完你能做到什么**：对工作量有准确预期，知道每个缺口对应改哪里、参考哪篇文档。
> **前置条件**：跑通了[第四步](./05-第四步-跑通完整推荐链路.md)。

## 演示模式"假"在哪

| 环节 | 演示模式的做法 | 真实系统需要 | 改哪里 |
| --- | --- | --- | --- |
| 帖子数据 | thunder 启动时生成 200 条模拟帖子（`--demo-seed-posts`） | 业务系统把发帖/删帖事件写进 Kafka topic `in-network-events`（Protobuf 格式，见 `proto/definitions/in_network.proto`），thunder 以正常模式消费 | 搭 Kafka + 写一个生产者；thunder 侧代码已就绪 |
| 关注列表 | `DemoStratoClient` 固定返回 101~105 | 从你平台的用户关系服务读取 | 用真实 adapter 替换 `home-mixer/clients/strato_client.rs` 的 `DisabledStratoClient` |
| 用户行为序列 | `DemoUserActionSequenceFetcher` 合成 32 条浏览记录 | 从你平台的行为日志系统读取（这是个性化的核心输入） | 用真实 adapter 替换 `home-mixer/clients/uas_fetcher.rs` 的 `DisabledUserActionSequenceFetcher` |
| 帖子内容 | `DemoTESClient` 为每条帖子编一句占位文本 | 从你平台的内容服务批量读取正文、媒体信息 | 用真实 adapter 替换 `home-mixer/clients/tweet_entity_service_client.rs` 的 `DisabledTESClient` |
| 作者资料 | 返回空（昵称、粉丝数缺失） | 从你平台的用户服务读取 | 用真实 adapter 替换 `DisabledGizmoduckClient` |
| 内容审核 | Demo VF 显式 Allow | 接你平台的审核服务，并定义漏返回/超时/附属内容策略 | 用真实 adapter 替换 `DisabledVisibilityFilteringClient` |
| 模型权重 | 随机初始化（或你训练的 checkpoint） | 用真实行为数据持续训练、定期发版 | [第三步](./04-第三步-训练自己的模型.md) + [训练指引](../../phoenix/docs/训练指引.md) |
| 网外候选池 | Phoenix 网关默认合成 2000 条并现场编码；`run_demo.sh` 传 `--corpus-size 1000` | 离线批量编码全量帖子，建向量索引（FAISS/Milvus），定期刷新 | `phoenix/services/grpc_gateway.py` 的 `RetrievalEngine` |
| 已看过帖子 | 请求里不带 | 客户端维护曝光记录（`seen_ids` / 布隆过滤器字段协议已就绪） | 客户端 + `proto/definitions/home_mixer.proto` |

一个设计上的关键点：**这些演示环节全部是客户端接口（trait）的独立 `Demo*` 实现**。`HomeMixerConfig` 解析 `HOME_MIXER_MODE=demo`，`HomeMixerServer::build` 将 mode 显式传给 `PhoenixCandidatePipeline::assemble_for_mode()`；Pipeline 不会再次读取环境变量选择依赖。默认降级实现以 `Disabled*` 命名，`production_ready` 在关键合同缺失时拒绝启动。替换时实现对应 trait、在具名 `PhoenixDependencies` 装配处注入，并补齐合同验收，不需要改流水线或演示代码。

## 建议的推进顺序

1. **先通数据，再通模型**：把 Kafka 事件流和帖子内容服务接上（前两行），此时用随机模型也能得到"新鲜度+多样性"驱动的可用 Feed。
2. **积累行为日志，训练第一版模型**：按[训练数据规格](../training/training_data_spec.md)落日志表，用[训练指引](../../phoenix/docs/训练指引.md)建立"日志 → 样本 → checkpoint"的例行任务。
3. **上线真实召回**：离线编码全量帖子建向量索引，替换演示候选池；索引切版和数据运维的设计建议见[数据运维手册](../operations/data_operations_runbook.md)。
4. **补齐工程保障**：监控告警（thunder / home-mixer 已埋 Prometheus 指标点）、灰度发布、降级策略（Phoenix 挂了自动退化为纯网内 Feed——这个行为现在就有）。

## 已知的工程缺口

坦白列出目前代码里需要注意的点：

- home-mixer 的 metrics HTTP 端口（9090）目前是空路由，指标已定义但未暴露。
- thunder 在 Kafka 消费追平前不会打印 `Server ready`（端口已监听，但查询只返回已摄入的部分数据，结果不完整）；`--kafka-batch-size` 默认 1000 条起批，小流量环境要调小。
- gRPC 网关是单进程 JAX 推理，生产需要按 QPS 做批处理和多副本（HTTP 版的生产化清单见 `phoenix/services/README.md`）。
- 各模块更细的风险清单在模块文档里：[home-mixer](../home-mixer/06-current-behavior-risks-roadmap.md)、[thunder](../thunder/06-risks-and-roadmap.md)、[candidate-pipeline](../candidate-pipeline/06-risks-tests-and-roadmap.md)。
