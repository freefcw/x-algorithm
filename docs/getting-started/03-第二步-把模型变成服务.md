# 第二步：把模型变成服务

> **这篇解决什么问题**：把上一步的模型包装成常驻的网络服务，让其他程序能调用。
> **读完你能做到什么**：起两个 HTTP 服务，用 curl 拿到打分和召回结果。
> **前置条件**：完成 [02-第一步-跑通模型演示](./02-第一步-跑通模型演示.md)。

以下命令都在 `phoenix/` 目录下执行。

## 启动服务

```bash
uv run scripts/run_services.py all
```

会同时启动两个 HTTP 服务（JAX 初始化需要约 1 分钟）：

| 服务 | 地址 | 干什么 |
| --- | --- | --- |
| 精排服务 | http://localhost:8081 | 给一批候选帖子打分排序 |
| 召回服务 | http://localhost:8082 | 从候选池检索 Top-K 帖子 |

预期日志末尾出现：

```text
All services started!
Ranker:     http://localhost:8081
Retrieval:  http://localhost:8082
```

也可以只启动其中一个：`uv run scripts/run_services.py ranker`（或 `retrieval`）。

## 调用打分接口

另开一个终端：

```bash
curl -s -X POST http://localhost:8081/v1/rank \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user_1", "candidate_ids": ["post_a", "post_b", "post_c"]}'
```

预期返回（数值会不同）：

```json
{
  "user_id": "user_1",
  "candidates": [
    {"candidate_id": "post_b", "rank": 1, "favorite_prob": 0.5, "overall_score": 0.5, ...},
    ...
  ],
  "inference_time_ms": 15.3,
  "strategy": "phoenix",
  "model_version": "random"
}
```

注意 `"model_version": "random"`——仍是随机权重。这个服务的用户特征来自内置的模拟特征库（`services/feature_store.py`），所以适合验证接口和压测，不代表推荐质量。

## 调用召回接口

```bash
curl -s -X POST http://localhost:8082/v1/retrieve \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user_1", "top_k": 5}'
```

预期返回一个按相似度排序的 `results` 列表，`corpus_size` 为 10000（内置模拟候选池）。

## 健康检查与接口文档

- `GET /health`：服务状态与模型版本。
- 浏览器打开 `http://localhost:8081/docs`：FastAPI 自动生成的交互式接口文档。

按 `Ctrl+C` 停止服务。

## 还有一个 gRPC 版本

上面的 HTTP 服务适合人调试。整条推荐链路里，home-mixer（Rust）与 Phoenix 之间走的是 **gRPC** 协议（协议定义在 `proto/definitions/recsys.proto`），对应的服务是：

```bash
uv run scripts/run_grpc_gateway.py    # 监听 50053 端口
```

它会在[第四步](./05-第四步-跑通完整推荐链路.md)里被 home-mixer 调用，这里先不用管。
