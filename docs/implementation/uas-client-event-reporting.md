# 客户端行为事件上报说明（UAS）

> **读者**：iOS / Android / Web 客户端、埋点通道、mrpyq 转发层  
> **日期**：2026-09-16  
> **配套**：消费端合同 [uas-event-contract.md](./uas-event-contract.md)；身份空间 [mrpyq-member-dimension-requirements.md](./mrpyq-member-dimension-requirements.md)

本文只讲客户端要发什么。服务端点赞 / 评论落库后的事件仍由后端自己发；客户端负责**只有端上才知道**的动作，以及**所有事件上的 `product_surface`（用户当时在哪个入口）**。

---

## 1. 这条事件是什么

用户对一条帖子做完一个动作后，发一条 JSON。推荐服务用它拼「这个皮最近对哪些帖做了什么」，作为 Phoenix 召回 / 精排的历史序列。

- **一条动作一条消息。** 同一条帖先点进详情再点赞，是两条。
- **不要发曝光。** 只是刷到、看见、划过，不要发。没有「看过」这个动作编号，发了也会被丢掉。
- **不要发撤销。** 取消点赞、取消关注、解除拉黑没有对应编号。

没有这类事件时，该用户走规则排序，模型不参与。

---

## 2. 怎么送到推荐侧

客户端 **不要** 直连 Kafka。组好下面的 JSON，走现有埋点 / 行为上报通道；mrpyq 收到后 **字段原样** 写入 UAS topic（一条 Kafka message = 一个 JSON 对象，UTF-8，无数组、无外层 envelope）。

上报 URL、鉴权、批量打包由 mrpyq 定。无论中间怎么包，落到 topic 里的 value 必须是 §3 这一份对象。

---

## 3. JSON 字段（落地到 topic 的 value）

| 字段 | 类型 | 必填 | 含义 | 规则 |
|---|---|---|---|---|
| `user_id` | string | 是 | **当前操作的皮** `member_id`，不是登录账号 | 24 位小写 hex，不能全 0 |
| `tweet_id` | string | 是 | 被操作帖子的 `feed_id` | 同上 |
| `author_id` | string | 是 | 该帖作者的 `creator_member_id` | 同上 |
| `action_time_ms` | int64 | 是 | 动作**发生**时刻，UTC epoch **毫秒** | `> 0`；用动作完成时间，不要用发送时间 |
| `action_type` | int32 | 是 | 动作编号，见 §5 | 整数 `1..=18`。不要发字符串 |
| `product_surface` | int32 | **是** | 动作发生时用户所在的入口，见 §4 | 整数 `0..=15`。不要发 `"home"` / `"timeline"` |

三个 ID 必须是皮维度的 ObjectId，和首页推荐请求里的 `viewer_id`、内容接口里的 `feed_id` / `creator_member_id` 同一套。混进 `account_id`、`user_id`、`user_no`，模型历史会对错人。

格式错了这条会被丢掉（记 invalid，不重试）。客户端发错 = 这条行为对推荐不存在。

### 示例

首页推荐里点赞：

```json
{"user_id":"66f1a2b3c4d5e6f708192a3b","tweet_id":"66f1a2b3c4d5e6f708192a3c","author_id":"66f1a2b3c4d5e6f708192a3d","action_time_ms":1789516800000,"action_type":1,"product_surface":0}
```

搜索结果里点进详情：

```json
{"user_id":"66f1a2b3c4d5e6f708192a3b","tweet_id":"66f1a2b3c4d5e6f708192a3c","author_id":"66f1a2b3c4d5e6f708192a3d","action_time_ms":1789516800500,"action_type":6,"product_surface":2}
```

## 4. `product_surface`：用户当时在哪个入口

这是**页面 / 入口**，不是动作本身。点赞永远是 `action_type=1`；在首页点还是在搜索里点，靠这个字段区分。

必须发 **整数**。模型词表只有 16 个槽（`0..=15`）。未列出的入口先找最接近的已有值；对不上再找推荐侧要一个新编号，**不要私自占用 4–15**。

| 值 | 入口 | 客户端怎么判 |
|---|---|---|
| `0` | 首页推荐（For You） | 推荐 Feed / 默认首页 |
| `1` | 关注流 | Following / 已关注时间线 |
| `2` | 搜索 | 搜索结果、搜索中间页里的帖 |
| `3` | 话题 / 标签 | 话题页、标签聚合页 |
| `4`–`15` | 预留 | 未分配。未经推荐侧确认不要用 |

判入口的原则：**动作发生时用户正在看的那个列表 / 页面**，不是帖子「属于」哪个频道。

- 从首页点进详情再点赞：`product_surface=0`（仍算首页链路）。
- 从搜索点进详情再分享：`product_surface=2`。
- 推送 / 站外深链打开详情：若没有对应编号，先用 `0`，并告知推荐侧，不要发明 `99`。
- 缺省、拿不到入口：发 `0`。不要省略字段（新上报必须带）；也不要发字符串。

同一条帖在两个入口都互动，发两条，各带当时的 surface。消费端按帖聚合时，**保留该帖最早一条行为的 surface**。

---

## 5. `action_type`：客户端要发哪些动作

编号是 `proto/definitions/phoenix_recsys.proto` 的 `ActionName`，从 **1** 起，不是从 0 起，也不是训练文档里那套 `favorite=0`。

### 5.1 必须报（客户端完成时立刻发）

| 值 | 产品动作 | 触发时机 |
|---|---|---|
| `6` | 点进帖子详情 | 从 Feed / 列表进入详情页 |
| `9` | 分享（任意渠道） | 分享面板任一渠道完成 |
| `10` | 通过私信 / 站内消息分享 | 发送完成 |
| `11` | 复制帖子链接 | 复制完成 |
| `15` | 不感兴趣 | 用户点了「不感兴趣」 |
| `16` | 拉黑作者 | 拉黑成功（若只在端上确认，端上发；若等服务端回包，由服务端发，**不要两边各发一条**） |
| `17` | 静音作者 | 同拉黑 |
| `18` | 举报帖子 | 举报提交成功 |

复制链接分享：发 `9` 和 `11` **两条**（同一 `tweet_id` / `author_id` / `product_surface`，`action_time_ms` 可以相同或相差几毫秒）。私信分享：发 `9` 和 `10` 两条。

### 5.2 有能力就报

| 值 | 产品动作 | 触发时机 |
|---|---|---|
| `5` | 点开大图 | 图片放大成功 |
| `7` | 点作者头像 / 进作者主页 | 进入作者页 |
| `8` | 视频有效观看 | 连续观看 ≥ 10 s 或播完；每条帖每次会话最多一次 |
| `12` | 停留 | 帖子在可视区停留 ≥ 2 s，每条帖一次 |

### 5.3 通常由服务端发（客户端不要重复发）

| 值 | 产品动作 | 说明 |
|---|---|---|
| `1` | 点赞 | 服务端落库成功后发。客户端不要在点按钮时先发 |
| `2` | 评论 / 回复 | 同上 |
| `14` | 从帖子上关注作者 | 关注落库成功后发 |

如果某条链路暂时没有服务端事件、只有客户端回包，可以先由客户端发，但同一动作只能有一个生产者。

### 5.4 不要发

| 值 / 类别 | 原因 |
|---|---|
| `3` 转发、`4` 引用、`13` 点引用帖 | 产品没有这些功能 |
| `0`、`19`、`20` | 消费端直接拒绝 |
| 曝光 / 浏览 / 划过 | 不是互动，进不了序列 |
| 取消点赞、取消关注等 | 没有编号 |

---

## 6. 身份与时间

- `user_id`：当前选中的皮，和推荐请求的 `viewer_id` 相同。
- `tweet_id` / `author_id`：列表或详情接口下发的 `feed_id`、`creator_member_id`，不要用展示用数字号。
- `action_time_ms`：毫秒。时钟和服务器对时；快于服务器超过 5 分钟的事件会被跳过，早于 7 天的也会被跳过。

重复发送同一条（六个字段都相同）是安全的，消费端写入幂等。

---

## 7. 客户端自检清单

发到测试环境后，用下面几条对照，避免上线才发现整批被丢：

- [ ] 每个动作一条 JSON，不是数组
- [ ] 三个 ID 都是 24 位小写 hex
- [ ] `action_type`、`product_surface` 都是 **JSON 数字**，不是 `"6"` / `"home"`
- [ ] 首页用 `0`，关注流 `1`，搜索 `2`，话题 `3`
- [ ] 详情页里的赞 / 分享沿用**进入详情前的入口**，不要一律写成 0（除非就是从首页进来）
- [ ] 没有曝光事件
- [ ] 点赞 / 评论没有和后端重复发
- [ ] 复制链接同时发了 9 和 11

服务端可用（不需要 Kafka）：

```bash
cat events.jsonl | UAS_REDIS_URL=redis://localhost:6379/ RUST_LOG=info cargo run -p home-mixer --bin uas-worker
```

日志里不应出现 `dropping invalid UAS event`。Redis 成员应类似：

```json
{"version":2,"tweet_id":"...","author_id":"...","action_time_ms":...,"action_type":6,"product_surface":2}
```
